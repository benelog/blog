## 우선 수정할 사항

### 1. 역할별 접미어 분리가 쓰임새 논쟁까지 피한다고 서술함

**위치: 본문 241행.** "뒤에서 제안하는 역할별 접미어 분리는 이 두 논쟁을 함께 피하는 방법입니다."라고 쓴다.

같은 문단 앞부분은 이름 논쟁(원격 호출이 없으면 DTO라는 이름이 원래 정의와 맞지 않는다)과 쓰임새 논쟁(로컬 맥락에서는 DTO를 둘 이유가 약하다)을 구분한다. 접미어를 `Response`, `Row` 등으로 바꾸면 이름 논쟁은 피하지만, 그런 객체를 두고 도메인 모델과 매핑하는 비용은 이름과 관계없이 그대로 남는다. Fowler가 LocalDTO에서 문제 삼은 것은 이 매핑 비용이다. 300행도 접미어 분리의 효과로 "원격 호출과 관련되지 않은 계층에서 쓰이는 객체를 DTO라고 부를 때 엄밀한 정의에서 벗어난다는 논쟁"만 들어서 241행과 범위가 다르다.

수정 제안:

> 뒤에서 제안하는 역할별 접미어 분리는 이름 논쟁을 피하는 방법입니다. 그런 객체를 둘지 말지는 이름과 별개로, 모델 사이의 불일치처럼 매핑 비용을 감수할 이유가 있는지로 판단해야 합니다.

근거: [Martin Fowler, LocalDTO](https://martinfowler.com/bliki/LocalDTO.html) ("I don't think it's worth the cost of all of that data mapping").

소스 대조 판정. Codex 지적 7번을 Claude가 재검증해 채택했다.

**반영 완료(제안과 다른 문장).** 글쓴이 확인 결과, 접미어 제안은 그런 객체를 추가로 두자는 주장이 아니다. 객체를 둘지는 별개로 결정하고, 두기로 했다면 `*Dto` 대신 역할에 맞는 이름을 붙이자는 뜻이다. 이 의도에 맞춰 다음 문장으로 바꿨다.

> 뒤에서 제안하는 역할별 접미어 분리는 이 중 이름 논쟁에 대한 답입니다. 그런 객체를 둘지는 쓰임새 논쟁에서 따로 판단할 문제이고, 두기로 결정했다면 ``Dto``보다 역할이 드러나는 이름을 붙이자는 제안입니다.

## 표현을 보완할 사항

### 1. Evans가 불변성을 정의에 넣지 않았다는 판단을 사실처럼 단정함

**위치: 본문 133행, 151행.** 133행은 "Fowler와 Evans의 문장을 자세히 보면 두 사람 모두 불변성을 VO의 정의에 포함하지는 않았습니다"라고 쓰고, 151행은 Evans의 해법 문단을 분류 기준과 설계 지침으로 나눠 읽는다.

Fowler의 경우 현재 bliki 글이 불변성을 "To avoid aliasing bugs"라는 목적에 딸린 규칙으로 제시하고, c2 wiki에서는 가변 value object를 전제한 조언을 하므로 본문의 판단을 뒷받침한다. Evans의 DDD Reference(인쇄 12쪽)는 분류 기준("When you care only about ...")과 "Treat the value object as immutable", "Don't give a value object any identity"를 한 해법 문단에 명령문으로 나란히 쓴다. 본문이 정의 요소로 보는 식별성 없음("Don't give a value object any identity")도 같은 명령문 형식이어서, 문장 형식만으로 앞 문장은 정의이고 뒤 문장은 권고라고 가를 근거는 약하다. Evans 쪽은 글쓴이의 해석이라고 밝히는 편이 정확하다.

수정 제안(133행 첫 문장):

> 그런데 Fowler의 문장을 자세히 보면 불변성을 VO의 정의에 포함하지는 않았습니다.

수정 제안(151행 첫 두 문장):

> Evans의 해법 문단은 분류 기준과 불변성 지침을 한 문단에 나란히 씁니다. 저는 이 문단을, value object로 분류하는 기준은 모델 요소의 속성과 로직에만 관심이 있는가이고 "Treat the value object as immutable."은 그렇게 분류한 객체를 다루는 방법을 권고하는 문장으로 읽습니다.

근거: [Eric Evans, Domain-Driven Design Reference (2015), Value Objects](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf), [Martin Fowler, Value Object](https://martinfowler.com/bliki/ValueObject.html).

소스 대조 판정. Codex 지적 1번.

**반영 완료(제안과 다른 문장).** 글쓴이 요청에 따라 Fowler를 빼지 않고, Evans가 불변성을 명령형 문장으로 썼다는 사실을 드러냈다. 133행은 "불변성은 VO의 정의가 아니라 지침으로 나옵니다. Fowler는 별칭 문제를 피하기 위한 규칙으로, Evans는 명령형 문장으로 불변성을 권합니다."로 바꿨다. 151행은 "Evans는 불변성을 명령형 문장으로 썼습니다."로 시작하고, 끝에 "저는 이 문장들을 분류 기준이 아니라, 분류한 객체를 다루는 방법에 대한 권고로 읽습니다."를 덧붙여 해석임을 밝혔다.

### 2. Valhalla의 value object를 DDD VO와 "핵심 성질이 같은 개념"이라고 한 뒤 같은 문단에서 "같은 개념이 아니지만"이라고 씀

**위치: 본문 68행.**

한 문단 안에서 둘째 문장은 "DDD와 Fowler가 말하는 Value Object와 핵심 성질이 같은 개념입니다"라고 하고, 마지막 문장은 "같은 개념이 아니지만"이라고 한다. 두 개념은 식별성을 다루는 수준이 다르다. DDD의 식별성은 도메인에서 개념적으로 구별할 필요가 있는가의 문제이고, 일반 클래스나 record로 만든 DDD VO도 JVM에서는 객체 식별성(`==`로 구분되는 참조)을 가진다. JEP 401은 이 런타임 객체 식별성 자체를 없앤다.

수정 제안(둘째 문장):

> DDD와 Fowler가 말하는 Value Object와는 식별성 없이 값으로 구분된다는 공통점이 있습니다. 다만 DDD의 식별성은 도메인 개념의 문제이고, Valhalla의 식별성은 JVM이 객체를 구분하는 런타임 성질이라는 차이가 있습니다.

근거: [JEP 401: Value Objects (Preview)](https://openjdk.org/jeps/401) Summary ("immutable and lack object identity").

소스 대조 판정. Claude가 먼저 찾았고 Codex 지적 4번과 겹친다.

**반영 완료.**

### 3. record의 자동 동등성이 도메인의 값 동등성과 다를 수 있다는 점이 빠짐

**위치: 본문 49~65행.** "두 record 인스턴스는 타입이 같고 구성 요소의 값이 모두 같을 때 동등합니다"라고 쓰고 `Money(BigDecimal, Currency)` 예제를 든다.

JEP 395의 서술("contain equal component values")과 일치하므로 틀린 문장은 아니다. 다만 참조 타입 구성 요소는 그 타입의 `equals()`로 비교하는데, `BigDecimal.equals()`는 scale까지 비교한다. 그래서 `new BigDecimal("10000")`과 `new BigDecimal("10000.0")`으로 만든 두 `Money`는 같은 금액인데도 동등하지 않다(JDK 25에서 실행해 `false` 확인). 예제로 든 타입이 바로 이 경우라서 한 문장 덧붙일 가치가 있다.

수정 제안(65행 코드 블록 뒤에 추가):

> 다만 record는 구성 요소 타입의 ``equals()``를 그대로 쓰므로, 자동 생성된 동등성이 도메인에서 원하는 동등성과 다를 수 있습니다. 예를 들어 ``BigDecimal``의 ``equals()``는 scale까지 비교하므로 ``10000``과 ``10000.0``으로 만든 ``Money``는 서로 다른 값이 됩니다. 이럴 때는 생성자에서 값을 정규화하거나 ``equals()``를 직접 정의합니다.

근거: [JEP 395: Records](https://openjdk.org/jeps/395), [BigDecimal.equals Javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/math/BigDecimal.html#equals(java.lang.Object)).

실행 확인. Codex 지적 3번.

**반영 완료.**

### 4. record로는 별칭 문제를 "막을 수 없다"고 단정함

**위치: 본문 113행.** "``Meeting``을 record로 선언해도 이 문제는 막을 수 없습니다."라고 쓴다.

기본 형태의 record는 막지 못하지만, record도 compact 생성자에서 `Date`를 복사해 저장하고 접근자를 직접 선언해 복사본을 반환하면(방어적 복사) 이 예제의 별칭 문제를 막을 수 있다. JEP 395는 접근자를 명시적으로 선언하는 것을 허용한다. 뒤 문장의 이유 설명은 맞다.

수정 제안:

> ``Meeting``을 record로 선언하는 것만으로는 이 문제를 막을 수 없습니다.

근거: [JEP 395: Records](https://openjdk.org/jeps/395) (explicitly declared accessor, compact canonical constructor).

### 5. Wikipedia를 "정의의 일부로 서술하는 자료"로 분류했지만 원문은 should를 씀

**위치: 본문 195행.**

Wikipedia 원문은 "Value objects should be immutable: this is required for the implicit contract that two value objects created equal, should remain equal."이다. 본문은 171~184행에서 should를 권고로 읽어야 한다고 논증하는데, 같은 should를 쓴 Wikipedia를 불변성을 정의로 보는 쪽에 넣으면 논증과 부딪힌다. 뒤의 "is required"가 정의에 가까운 위상을 주는 것은 맞으므로 두 표현을 함께 드러내는 편이 공정하다.

수정 제안:

> * Wikipedia는 value object가 불변이어야 한다(should)고 쓰면서, 같은 값으로 생성된 두 value object가 계속 같아야 한다는 암묵적 계약을 위해 불변성이 필요하다(required)고 설명합니다. should를 쓰면서도 불변성을 계약의 전제로 둔다는 점에서 정의에 가까운 위상을 부여합니다.

근거: [Wikipedia: Value object](https://en.wikipedia.org/wiki/Value_object) 첫 절.

### 6. LocalDTO의 "해롭다"를 서비스 계층 논거에 대한 답으로 요약함

**위치: 본문 221행.** "그래서 서비스 계층의 클라이언트가 도메인 모델에 의존하지 않도록 서비스 계층 API에 DTO를 두자는 주장에 대해, 로컬 맥락에서는 DTO가 필요하지 않을 뿐 아니라 오히려 해롭다고 말합니다."라고 쓴다.

원문의 순서는 반대다. "Not just do you not need them in a local context, they are actually harmful ..."은 로컬 맥락 전반에 대한 판단으로 먼저 나오고, 서비스 계층 논거("Some people argue for them as part of a Service Layer API ...")에는 그 뒤에 "While that may be handy, I don't think it's worth the cost of all of that data mapping."이라고 따로 답한다. 인용 블록(225행)은 정확하므로 요약 문장만 원문 순서에 맞추면 된다.

수정 제안:

> 그래서 로컬 맥락에서는 DTO가 필요하지 않을 뿐 아니라 오히려 해롭다고 말합니다. 한 번의 호출로 많은 데이터를 주고받는 coarse-grained API는 사용하기 불편하고, 도메인 계층이나 데이터 소스 계층에서 DTO로 데이터를 옮기는 작업이 모두 추가 비용이라는 이유입니다. 서비스 계층의 클라이언트가 도메인 모델에 의존하지 않도록 서비스 계층 API에 DTO를 두자는 주장에 대해서도, 편리할 수는 있지만 그 모든 데이터 매핑 비용을 들일 가치는 없다고 답합니다.

근거: [Martin Fowler, LocalDTO](https://martinfowler.com/bliki/LocalDTO.html).

소스 대조 판정.

**반영 완료.**

### 7. LocalDTO가 인정한 다른 로컬 용도가 빠져 결론의 범위가 좁음

**위치: 본문 230~239행.** 모델 불일치를 로컬 DTO가 유용한 경우로 소개하고 "Fowler의 비판은 도메인 모델과의 분리 자체를 목적으로 DTO를 두는 경우를 향한 것"이라고 정리한다.

LocalDTO 원문 끝의 Update는 멀티스레드 애플리케이션에서 격리 영역(isolate) 사이에 메시지 큐로 DTO를 주고받는 용도도 인정한다. 또 DTO 카탈로그의 2013-08-11 Note는 원격 호출 묶기가 주된 이유이지만 직렬화 메커니즘을 캡슐화하는 장점도 언급한다. 결론 문장 자체는 틀리지 않지만, "다만 같은 글에서"로 시작하는 230행이 예외를 하나만 드는 것처럼 읽힌다.

수정 제안(239행 끝에 추가):

> 같은 글의 뒷부분에는 멀티스레드 애플리케이션에서 격리된 영역 사이에 메시지로 데이터를 주고받을 때 DTO를 쓰는 용도도 덧붙여 있습니다.

근거: [Martin Fowler, LocalDTO](https://martinfowler.com/bliki/LocalDTO.html) Update 문단, [Data Transfer Object 카탈로그](https://martinfowler.com/eaaCatalog/dataTransferObject.html) 2013-08-11 Note.

소스 대조 판정. Codex 지적 6번.

**반영 완료.**

### 8. `Date`를 `LocalDateTime`으로 바꾸는 것이 같은 개념의 대체처럼 읽힘

**위치: 본문 115행.** "시작 시각을 ``LocalDateTime``으로 바꾸면"이라고 쓴다.

`Date`는 타임라인상의 한 시점(epoch 기준 밀리초)이고 `LocalDateTime`은 시간대 없는 날짜·시각이라서 표현하는 개념이 다르다. 불변성 예제로는 유효하고, 회의 시각처럼 지역 시각으로 다루는 도메인에서는 자연스러운 선택이다. 다만 `Date`를 쓰던 코드를 그대로 옮기는 안내로 읽히면 시간대 정보가 빠지는 문제를 놓칠 수 있다. 짧게 단서를 달거나, 시점 그대로 옮기려면 `Instant`(`plus(Duration.ofHours(1))`)를 쓴다고 적는 방법이 있다.

수정 제안(115행 둘째 문장):

> 시작 시각을 시간대 없는 날짜·시각인 ``LocalDateTime``으로 표현하면 ``plusHours()``가 기존 인스턴스를 고치지 않고 새 인스턴스를 반환하므로, 인스턴스를 공유해도 다른 회의의 시작 시각은 바뀌지 않습니다.

근거: [java.time 패키지 Javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/package-summary.html).

소스 대조 판정. Codex 부가 지적.
