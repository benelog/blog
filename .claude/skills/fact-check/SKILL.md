# 사실 관계 검증 (fact-check)

글의 주장·인용·수치가 1차 출처와 맞는지 확인하고, 그 결과를 저장소 루트의 `fact-checks/`에 남기는 작업이다.
검증 기록은 글과 함께 저장소에 남아 나중에 다시 검토할 때 출발점이 된다.
따라서 기록에는 "무엇을 어떤 근거로 확인했고, 무엇은 확정하지 못했는가"가 드러나야 한다.

역할 분담이 핵심이다. **Codex는 의심 지점을 찾는 리뷰어이고, 재검증과 기록 작성은 Claude가 한다.**
Codex는 읽기 전용 샌드박스에서 돌기 때문에 파일을 쓰지 못하고, Codex의 지적은 틀릴 수도 있다.
그래서 Codex 프롬프트에는 "기록을 남겨라"는 요청을 넣지 않고, Claude가 지적을 1차 출처로 다시 확인한 뒤 기록을 쓴다.

이 작업은 **리뷰 전용**이다. 사용자가 반영을 요청하기 전에는 글 본문을 고치지 않고, 커밋도 요청할 때만 한다.
수정 제안은 기록 안에 문장 단위로 적어 두어 사용자가 판단하게 한다.

## 전체 흐름

1. 검증 대상과 기준 커밋을 정한다.
2. Codex 적대적 리뷰를 돌려 의심 지점을 넓게 모은다.
3. Codex의 지적과 글의 핵심 인용을 Claude가 1차 출처로 직접 재검증한다.
4. Claude가 `fact-checks/<글-slug>-<YYYY-MM-DD>.md`에 기록을 쓴다.
5. 결과를 사용자에게 보고한다. 본문 수정과 커밋은 요청이 있을 때만 한다.

## 1. 대상과 기준 커밋

사용자가 말한 범위를 그대로 따른다. 판단 기준은 다음과 같다.

* "방금 커밋", "최근 커밋": 작업 트리가 깨끗하면 `git diff --stat HEAD~1...HEAD`로 범위를 확인하고 기준 커밋을 `HEAD`로 잡는다.
* 작업 트리에 변경이 있으면 작업 트리 전체가 대상이고, 기준 커밋은 `HEAD`에 "미커밋 변경 포함"이라고 적는다.
* 글 파일을 지목하면(예: `src/content/foo.adoc`) 글 전체가 대상이다. 변경분이 아니라 본문 전체를 읽는다.

기록 파일 이름은 글의 slug(확장자를 뺀 `.adoc` 파일 이름)에 오늘 날짜를 붙인다.
같은 글의 이전 기록이 `fact-checks/`에 있으면 머리말에서 링크하고, 이전 판정을 승계하지 않고 다시 대조한다.
같은 날 같은 글을 두 번 검증하면 두 번째 파일에 `-2` 접미사를 붙이고(예: `call-by-value-2026-09-19-2.md`), 제목에도 "(2차)"를 적는다.

## 2. Codex 적대적 리뷰

Codex는 글쓴이와 다른 눈으로 과도한 일반화, 빠진 예외, 인용 오독을 찾는 데 쓴다.
프롬프트에는 검증 초점만 적는다. 파일 작성이나 수정 요청은 넣지 않는다.

커밋 범위를 검증할 때:

```bash
node "$HOME/.claude/plugins/cache/openai-codex/codex/1.0.6/scripts/codex-companion.mjs" \
  adversarial-review --base HEAD~1 "<사용자의 검증 요청에서 초점 문장만>. 논리 전개와 사실 관계 검증 위주로. 각 지적에 본문 행 번호와 1차 출처 URL을 붙여라."
```

글 전체를 검증할 때(작업 트리가 깨끗해 diff가 없으면 `adversarial-review`는 검토할 것이 없다고 끝난다):

```bash
node "$HOME/.claude/plugins/cache/openai-codex/codex/1.0.6/scripts/codex-companion.mjs" \
  task "src/content/<slug>.adoc 전체의 논리 전개와 기술적 사실 관계를 검증하라. 각 지적에 본문 행 번호와 1차 출처 URL을 붙여라. 파일은 수정하지 마라."
```

`--write`는 붙이지 않는다. 플러그인 버전 디렉터리(`1.0.6`)가 바뀌었으면 `ls ~/.claude/plugins/cache/openai-codex/codex/`로 확인한다.
파일 하나 규모면 포그라운드로 기다리고, 여러 글이면 `--background`로 돌린 뒤 `status`로 확인한다.
Codex 출력은 그대로 보존해 두고, 다음 단계의 입력으로 쓴다. 사용자에게 보여 줄 때는 인용 블록으로 구분한다.

## 3. Claude의 재검증

Codex의 지적은 가설이다. 기록에 "확인" 또는 "수정"으로 적기 전에 Claude가 직접 근거를 본다.
Codex가 문제없다고 넘긴 부분도 글의 핵심 인용은 다시 본다. 리뷰어 두 명이 같은 곳을 놓칠 수 있기 때문이다.

* 인용문과 절 번호, 쪽 번호는 1차 출처(표준 문서, 언어 사양, 공식 매뉴얼, 소스 코드)를 WebFetch나 curl로 받아 원문과 글자 단위로 대조한다.
  WebFetch가 긴 페이지를 잘라 내면 curl로 받아 python이나 grep으로 해당 문장을 찾는다.
  원문을 확인하지 못한 인용은 기록에 "한계"로 적고, 본문에는 항목·절 이름만 남기라고 제안한다.
* 실행 결과(출력값, 성능 수치)는 가능하면 로컬에서 재현한다. 재현하지 못했으면 "소스 대조 판정"인지 "실행 확인"인지 구분해 적는다.
* Codex의 지적이 틀렸으면 기록에 "Codex 지적, 재검증 결과 기각"으로 남긴다. 근거 없이 지적을 버리지 않는다.
* 판정 용어는 세 가지로 고정한다. **확인**은 출처나 실행으로 뒷받침됨, **수정**은 오류나 과도한 일반화가 있어 고쳐야 함, **한계**는 이번 검증으로 확정할 수 없음.

이 저장소에서 자주 걸리는 유형은 [references/common-pitfalls.md](references/common-pitfalls.md)에 있다. 검증 전에 한 번 읽는다.

## 4. 기록 작성 (Claude가 직접)

형식은 [references/record-template.md](references/record-template.md)를 따른다. 실제 예는 `fact-checks/call-by-value-2026-09-19.md`와 `fact-checks/java-external-process-2026-09-13.md`다.

지켜야 할 점:

* 머리말에 대상 파일 상대 링크(`../src/content/<slug>.adoc`), 기준 커밋 해시(전체 40자), 이전 기록 링크, 범위, 방법, 결과 요약, 반영 상태를 적는다. 반영 상태는 처음에는 "미반영"이다.
* 수정 항목마다 위치(본문 행 번호), 무엇이 왜 틀렸는지, 수정 제안 문장, 근거 링크를 적는다. 행 번호는 기준 커밋 기준이라고 밝힌다.
* 확인한 항목은 표로 정리한다. 주장 | 판정 | 근거 세 칸이다. 재현 방식(소스 대조·실행)은 구분해 적는다.
* 문체는 기존 기록과 같은 문어체 평서형("~다")이다. 블로그 본문의 경어체와 다르다.
* 나중에 본문에 반영하면 항목마다 "반영 완료"와 반영 커밋을 덧붙여 갱신한다. 검증 당시의 제안 문장은 지우지 않는다.

## 5. 보고

사용자에게는 결과 요약, 우선 수정할 사항, 기록 파일 경로를 알린다.
본문을 고치라는 요청이 오면 그때 create-post와 korean-tech-writing 스킬을 따라 수정하고, 기록의 반영 상태를 갱신한다.
